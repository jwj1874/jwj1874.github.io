Pulse Compression→ MTI→ MTD→ CFAR→ Clustering

운용 모드(실시간 탐지맵·표적 리스트)·분석 모드(dwell 그래프·트랙맵)를 제공하는 C# WPF GUI와 연동하고, 통신 프로토콜(ICD) 문서를 직접 작성

문제 · 해결

CASE 01

문제

타겟 보드나 라이선스 상황에 따라 FFT/BLAS 연산 라이브러리가 바뀔 수 있는데, 그때마다 신호처리 파이프라인 코드를 다시 손대야 한다면 유지보수가 어려워짐.

해결

ArmPL / FFTW / NE10 세 백엔드를 빌드 타임 옵션으로 선택 가능하도록 추상화해, 백엔드가 바뀌어도 Pulse Compression → MTI → MTD → CFAR → Clustering 파이프라인 로직은 그대로 재사용.

CASE 02

문제

레이더는 dwell 주기 안에 처리를 끝내야 하는데, 스케줄러가 다른 프로세스에 밀리거나 스레드가 다른 코어로 옮겨가면 처리 시간이 들쭉날쭉해질 위험이 있었음.

해결

CPU 코어를 cset shield로 격리하고 OpenMP 스레드를 해당 코어에 고정, chrt -f 99로 FIFO 실시간 스케줄링을 적용. perf record/stat로 처리 시간을 실측하며 지연을 관리.

CASE 03

문제

ARM 타겟 보드가 없으면 신호처리 엔진을 개발·검증할 수 없어, 매번 실제 보드에 올려야만 동작을 확인할 수 있었음.

해결

각 처리 단계를 IPulseCompressor 등 인터페이스로 분리하고 연산 라이브러리를 Intel MKL로 교체한 x86 버전을 C++로 재작성(signal_processer_cpp)해, 보드 없이 개발 PC에서 알고리즘을 검증할 수 있게 함.

CASE 04

문제

x86 포팅 중, 원본 ARM 백엔드가 fast-time 샘플 수를 그대로 range bin 개수로 사용해 실제로 채워지지 않은 tail 구간이 MTI/MTD/CFAR/Clustering까지 그대로 흘러들어가는 것을 발견.

해결

유효 range 길이를 out_fast_time = fast_time - (num_pulse_samples - 1)로 재계산해 모든 단계에서 통일하고, 회귀 테스트로 재검증.

UGV System — 4축 로봇팔 무인 지상차량 제어 시스템

4축 로봇팔을 탑재한 무인 지상차량을 BLE로 원격 제어하는 시스템입니다. 컨트롤러 보드와 차량 보드를 각각 STM32F103 + FreeRTOS로 구성하고, 20ms 주기의 결정론적 제어 루프로 조향·회전·암 제어 명령을 송수신·전달하는 구조를 설계·구현했습니다.

20ms 주기로 osDelayUntil 기반 제어 루프가 조이스틱/버튼 상태를 읽어 패킷을 구성 → 송신하는 구조를 반복

문제 · 해결

CASE 01

문제

BLE(UART) 무선 구간은 노이즈에 취약해서, 패킷이 깨진 채로 수신되면 모터나 서보가 잘못된 값으로 오동작할 위험이 있었음.

해결

SOF(0xAA) + 14바이트 고정 길이 + XOR 체크섬으로 프레이밍한 자체 패킷 포맷을 설계해, 체크섬이 맞지 않는 패킷은 폐기하도록 구현.

CASE 02

문제

인터럽트(ISR) 안에서 체크섬 검증이나 디코딩 같은 무거운 처리를 하면 다음 인터럽트 응답이 늦어지고 시스템 전체가 불안정해질 수 있었음.

해결

UART Idle-line 검출 + DMA(HAL_UARTEx_ReceiveToIdle_DMA)로 가변 길이 패킷을 수신하고, ISR은 수신 이벤트만 메시지 큐(MOTER_QUEUE / SERVO_QUEUE)에 적재한 뒤 즉시 반환. 검증·디코딩은 Dispatcher 태스크 컨텍스트에서 처리.

CASE 03

문제

태스크 실행 시간이 매번 달라지면 osDelay만으로는 오차가 누적되어, 시간이 지날수록 실제 명령 송신 간격이 목표 주기(20ms)에서 점점 벌어짐.

해결

osDelayUntil로 절대 시각 기준 다음 실행 시점을 미리 계산해, 태스크 실행 시간과 무관하게 고정 주기를 유지하도록 구현.

CASE 04

문제

컨트롤러 하나로 주행(조이스틱)과 로봇팔 조작(서보)을 모두 지원해야 하는데, 두 입력 체계를 하나의 로직에 억지로 합치면 분기가 복잡해지고 확장이 어려워짐.

해결

공통 인터페이스 IController를 두고 조이스틱 컨트롤러와 서보 컨트롤러를 런타임에 교체하는 구조로 설계, SystemManager는 현재 어떤 컨트롤러가 붙어있는지 몰라도 되게 함.

CASE 05

문제

목표각을 서보에 그대로 넘기면 각도가 급격히 바뀔 때 로봇팔이 튀듯이 움직여 기구적 충격과 떨림이 발생.

해결

사다리꼴 속도 프로파일(가속-정속-감속)로 목표각까지 보간해, 현재각을 매 주기 갱신하며 부드럽게 움직이도록 구현. IPwmDriver/ITrajectory 인터페이스로 축(ServoAxis) 로직과 하드웨어 종속 코드를 분리.

문제 · 해결

CASE 01

문제

원래 타겟 보드였던 Jetson Orin NX를 구할 수 없게 되어, 임베디드 보드 위에서 동작하는 것을 전제로 짜둔 구조를 그대로 쓸 수 없었음.

해결

일반 PC에서 동작하는 애플리케이션으로 전체 구조를 다시 설계해, 보드 없이도 개발과 시연을 이어갈 수 있게 함.

CASE 02

문제

기존 단일 스레드 구조에서는 캡처 → 추론 → 추적 → 제어가 한 루프 안에서 순차 실행돼, 한 단계가 느려지면 파이프라인 전체가 같이 밀림.

해결

수신·추적·제어를 각각의 스레드로 분리하고, 조건변수 기반 ThreadSafeQueue로 단계 사이를 연결하는 파이프라인 구조로 재설계.

CASE 03

문제

YOLO 탐지 결과의 중심 좌표가 프레임마다 미세하게 흔들려서, 그대로 제어에 사용하면 액추에이터가 떨리듯 움직임.

해결

OpenCV Kalman Filter로 위치 추정을 안정화한 뒤, PID 컨트롤러로 화면 중심과의 오차를 제어값으로 변환해 시리얼(UART)로 STM32에 전달.

CASE 04

문제

탐지(Python/YOLO)와 제어(C++)가 언어와 실행 주기가 서로 다른데, 한 프로세스에 합치면 Python 쪽 지연이 제어 루프에도 영향을 줄 수 있음.

해결

두 프로세스를 UDP 소켓으로 분리해 독립적으로 동작시키고, 좌표(x, y, confidence)만 가볍게 주고받도록 구성.

Matter SDK 기반 스마트 화분

Matter(구 CHIP) SDK를 분석해 ESP32 위에 구현한 스마트 화분입니다. 자체 개발 앱뿐 아니라 Google Home, Apple Home에서도 같은 기기를 커미셔닝하고 제어할 수 있음을 직접 확인해, 특정 플랫폼에 종속되지 않는 스마트홈 기기를 만드는 것이 목표였습니다.

담당 영역: ESP32 펌웨어(센서/액추에이터 드라이버) 및 Matter SDK 연동 — 자체 앱 UI 개발은 별도 팀원 담당.

문제 · 해결

CASE 01

문제

스마트홈 기기를 자체 앱으로만 제어하게 만들면, 사용자가 이미 쓰고 있는 Google Home·Apple Home 생태계와 분리되어 특정 플랫폼에 종속되는 문제가 있음.

해결

Matter(CHIP) SDK를 분석해 표준 클러스터(OnOff, TemperatureMeasurement 등)로 기기를 구현, 자체 앱 외에 Google Home·Apple Home에서도 동일 기기를 커미셔닝·제어할 수 있음을 직접 확인.

CASE 02

문제

ESP32에서 온습도(DHT11)·조도(CDS)·토양수분·워터펌프·LED를 모두 제어하려면 각 부품에 맞는 드라이버가 필요한데, 참고할 수 있는 레퍼런스가 제한적이었음.

해결

각 부품의 드라이버(dht/cds_task/soil_task/water_pump/led)를 직접 작성하고, 공용 ADC 핸들로 여러 아날로그 센서를 멀티플렉싱해 읽도록 구현.

CASE 03

문제

기기가 리셋되거나 페어링이 끊기면 다시 앱에서 수동으로 커미셔닝해야 해서 번거로움.

해결

팹릭이 비어 있을 때 자동으로 커미셔닝 윈도우(DNS-SD, 300초)를 열고, 팩토리 리셋 버튼으로 즉시 재커미셔닝할 수 있도록 구현.
